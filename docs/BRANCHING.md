# 브랜치와 PR 규칙

이 저장소의 루트 컨벤션 문서다. [`CONTRIBUTING.md`](../CONTRIBUTING.md) 가 "무엇을
기여할 것인가" 를 말한다면, 이 문서는 "어떤 모양으로 올릴 것인가" 를 말한다.
두 문서가 어긋나면 이 문서가 우선한다.

## 브랜치 이름

접두어 + 소문자 kebab. 대문자·공백·`_` 는 쓰지 않는다.

| 접두어 | 용도 | 예시 |
|---|---|---|
| `feat/` | 지표 추가, 기능 추가 | `feat/paragraph-length-gini` |
| `fix/` | 계산 오류 수정, 오탐 수정 | `fix/bb-nimda-decompose` |
| `docs/` | 문서·예문·README 수정 | `docs/demolink-examples-07` |
| `research/` | 측정 실행, 가설 검증, 방향표 관련 | `research/proposal-genre-auc` |
| `corpus/` | 라벨 코퍼스·매니페스트 추가 | `corpus/proposal-40v20` |

작업은 기본적으로 `main` 에서 분기한다. `main` 은 항상 초록색이어야 한다.

## 이 저장소 특수 규칙 2가지

### 1. `research/` 브랜치 = 방향표를 뒤집을 수 있는 브랜치

`research/` 브랜치의 정의는 **결과가 가설의 방향을 뒤집는 작업**이다. 측정만 하고
아무것도 안 바뀌면 그건 `research/` 브랜치가 아니라 그냥 실행 기록이며, 그럴 땐
`docs/RESEARCH.md` 에 직접 커밋하면 된다.

- **`research/` 브랜치는 단독으로 머지하지 않는다.**
  `docs/RESEARCH.md` 갱신을 반드시 같은 PR 에 묶는다. 묶이지 않은 `research/` PR 은
  닫는다 — 근거 없는 방향 변경이 되돌아오지 않게 하는 것이 목적이다.
- 방향표를 뒤집는 경우 **반증 조건을 함께 적는다.** 어떤 결과가 나오면 다시 뒤집는지를
  남기지 않으면, 다음 사람은 같은 논리를 다른 숫자로 반복하게 된다.
- 장르 대칭이 없는 코퍼스로 얻은 AUC 은 방향표의 근거가 되지 못한다.
  `research/measure.py` 가 AUC 을 내지 않는 것은 버그가 아니라 게이트다.

### 2. `corpus/` 브랜치 = 공개 가능한 텍스트만

- **공개 가능한 텍스트만 넣는다.** 실전 공모 제출물, 기관 공고문, 실제 일반인이 쓴
  참여 의견은 **어떤 경우에도** 넣지 않는다. 동의를 받았거나 발신처가 공개된 경우도
  같다 — 개인 식별 정보가 남을 수 있고, 이 저장소가 공개 저장소이기 때문이다.
- 공개할 수 없는 자료가 있다면 **문서가 아니라 측정값만** 기여한다.
- 예문 세트(`eval/examples.json`)는 **자체 작성만** 허용한다. `meta.provenance` 는
  `"self-authored"` 로 고정된다.
- 예문 쌍은 `kept_facts` 의 수치·고유명사가 양쪽 원고에 **문자 그대로** 있어야 하고,
  분량은 ±3% 안이어야 한다. 의역은 리터럴이 아니다.
- `research-private/` 는 절대 커밋하지 않는다. `.gitignore` 에 있고, 커밋 accident 가
  이 저장소에서 가장 복구하기 어려운 사고다. `git status` 에 뜨면 커밋 전에 지운다.

## PR 제목

```
[종류] 한 줄 요약
```

`[종류]` 는 아래 넷 중 하나. 기능·수정을 새로 부르는 이름을 쓰지 않는다.

| 태그 | 쓰는 때 |
|---|---|
| `[지표]` | 지표를 추가하거나 계측 방식을 바꿈 |
| `[수정]` | 계산 오류, 오탐, 파싱 실패를 고침 |
| `[문서]` | 문서·예문·주석만 바꿈 |
| `[코퍼스]` | 라벨 코퍼스·매니페스트를 추가 |

예시:

```
[지표] 문단 단위 종결 레지스터 교차율 추가
[수정] ㅂ니다 끝 어미가 분해되지 않아 합쇼체가 plain 으로 분류되던 문제
[코퍼스] 제안서 장르 사람 40건 / 기계 20건 매니페스트
```

## 리뷰 기준

이 저장소의 제품은 **코드**가 아니라 **측정 신뢰성**이다.
리뷰어는 **수치 하나를 믿지 않는다.**

코드 diff 를 보기 전에 순서대로 본다.

1. **표본** — 몇 건인가. 18건으로 얻은 AUC 은 표본 오차 안이다.
2. **편향** — 두 라벨의 장르가 같은가. 다르면 문종 차이를 재고 있는 것이다.
   (`research/measure.py` 가 이걸로 AUC 을 내지 않는 이유다)
3. **재현성** — 같은 입력 → 같은 출력이 보장되는가. 의존성 0개, 네트워크 없음,
   모델 호출 없음. 이게 깨지면 계측값이 아니라 추측이 된다.
4. **반증 가능성** — 새 지표에 제거 조건이 있는가. 없는 지표는 영원히 살고,
   방향은 계측값이 원하는 쪽으로 움직일 때까지 뒤집힌다.
5. **마지막으로** — 그러고도 코드가 읽히는가.

리뷰어가 되기 위한 최소 요건: `docs/RESEARCH.md` 를 한 번은 읽은 것.
가설(H1~H4)과 P0 게이트를 모르고 리뷰하면, 이 저장소가 만들려던 실패를
그대로 통과시켜 버린다.

## 머지 순서

1. 테스트가 초록색인지 본다 (`.github/workflows/ci.yml`, Python 3.10~3.13).
2. `research/`·`corpus/` 브랜치는 위 특수 규칙을 먼저 확인한다.
3. `docs/RESEARCH.md` 갱신이 붙었는지 확인한다. 방향표가 바뀌었다면 반드시 붙어야 한다.
4. 문제없으면 머지한다. 방향표 변경과 코드 변경은 **따로** 머지한다 — 되돌릴 수 있어야 한다.
