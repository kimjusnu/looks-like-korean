# 화면 문구 (UX 라이팅)

기계 검사: `python -m looks_like_korean check 문구.txt --genre ui` (문구를 한 줄에 하나씩 넣은 파일)
근거: `docs/research/ux-writing.md` 2장·3장·4장

## 기준

- **서비스 전체에서 말투를 하나로 정한다.** 해요체든 합쇼체든 한 번 정하면 오류 메시지까지 같은 어미를 쓴다.
- 요청은 말투와 상관없이 「~해 주세요」로 쓴다. 「~하십시오」「~바랍니다」는 쓰지 않는다(약관·법적 고지 본문은 예외).
- 확인 질문은 해요체면 「~할까요?」, 합쇼체면 「~하시겠습니까?」. 해요체 제품의 「~하시겠어요?」는 과잉 존대다.

## 쓰기 전에 확인할 것

1. **이 서비스의 말투.** 기존 코드의 문구를 세어 「-요.」와 「-니다.」 중 많은 쪽을 따른다. 기존 문구가 없으면 한 번만 묻는다.
2. **문구가 놓일 자리.** 버튼, 토스트, 확인 창, 빈 화면, 입력 칸 오류 중 어디인가. 자리를 모르면 먼저 묻는다.
   토스트 자리에 세 문장을 쓰는 것이 가장 흔한 실수다.
3. **같은 대상을 부르는 용어.** 서비스 안에서 이미 쓰는 낱말을 찾아 그대로 쓴다.

## 쓰는 규칙

1. **버튼은 누르면 일어날 일을 동사로 쓴다.** [확인] [예] 대신 [삭제하기] [저장].
2. **오류는 상황·이유·해결 방법을 담는다.** 「오류가 발생했습니다」 한 줄로 끝내지 않는다.
3. **사용자를 탓하지 않는다.** 「올바른 정보를 입력하지 않으셨습니다」 대신 「생년월일은 8자리 숫자로 입력해 주세요」.
4. **뜻에 영향 없는 낱말을 뺀다.** 제목을 되풀이하는 설명, 인사말, 「성공적으로」.
5. **사용자가 쓰는 말로 쓴다.** 개발 용어(「세션」「토큰」「동기화 실패」)와 어려운 한자어를 피한다.
6. **능동으로 쓴다.** 「변경이 완료되었습니다」보다 「바꿨어요」.
7. **존대를 과하게 얹지 않는다.** 「파일이 준비되셨습니다」처럼 사물을 높이지 않는다.
8. **할 수 없는 것보다 할 수 있는 것을 쓴다.**
9. **빈 화면에는 비어 있는 이유와 다음 행동을 쓴다.**
10. **확인 창은 되돌릴 수 없는 일에만 띄운다.** 무엇이 사라지는지 구체적으로 쓴다.
11. **오류에는 사과·감탄사·농담·느낌표를 넣지 않는다.** 서비스 잘못이 분명할 때만 짧게 사과한다.
12. **이모지는 정보가 될 때만, 하나만.**

## 사람이 읽고 판단할 항목

- [ ] 같은 상황을 화면마다 다른 말로 쓰지 않았는가(「저장했어요」「저장 완료!」「성공적으로 저장되었습니다」)
- [ ] 문구 길이가 자리에 맞는가(버튼은 두 어절 안팎, 토스트는 한 문장)
- [ ] 톤이 상황에 맞는가(잔액 부족에 장난스러운 말을 쓰지 않는다)
- [ ] 특정 연령대를 겨냥한다며 억지 유행어를 넣지 않았는가

## 예문 (새로 지은 것)

| 자리 | 고치기 전 | 고친 후 |
|---|---|---|
| 오류 | 앗! 알 수 없는 오류가 발생했습니다 😢 | 인터넷 연결이 끊겼어요. 연결되면 다시 시도해 주세요. |
| 확인 창 | 정말 삭제하시겠습니까? [확인] [취소] | 사진 12장을 지울까요? 지운 사진은 되살릴 수 없어요. [지우기] [취소] |
| 빈 화면 | 데이터가 존재하지 않습니다. | 아직 저장한 장소가 없어요. 지도에서 별표를 누르면 여기에 모여요. |
| 입력 오류 | 입력값이 유효하지 않습니다. | 전화번호는 숫자만 입력해 주세요. |
